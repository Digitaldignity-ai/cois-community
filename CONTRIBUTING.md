# Contributing

Ideas, questions, documentation improvements and careful criticism are welcome. You do not need organization membership or direct write access: use an issue, a discussion, or a fork and pull request.

## Make a useful suggestion

1. Search existing issues and discussions for related ideas.
2. Choose a form in [New issue](https://github.com/Digitaldignity-ai/cois-community/issues/new/choose), or start a discussion if the idea is still taking shape.
3. Explain the problem, who it affects, and the result you would like. A small synthetic example helps.
4. Mention tradeoffs, alternatives and unanswered questions. Separate what you observed from what you infer.

No implementation or benchmark is required to propose an idea. Link public evidence when available and say when it has not been tested.

## Keep public contributions safe to share

Everything in ordinary issues, discussions, pull requests and commits is public. Do not post credentials, tokens, private keys, recovery material, private notebooks or transcripts, personal data, internal hostnames or addresses, or details of real private infrastructure. Check screenshots and attachments for this material too. Use synthetic examples and minimal redacted excerpts you are authorized to publish.

For a suspected vulnerability or data exposure, follow [SECURITY.md](SECURITY.md) instead of opening a public issue. This project does not authorize testing systems you do not own or have permission to assess. Posting a suggestion never authorizes an agent to execute it.

## Pull requests

Fork this repository, make a focused change, and explain the problem and resulting improvement. Link a related issue when there is one. Keep drafts clearly marked and describe any validation actually performed. Do not add executable workflows, runtime credentials or generated conversation archives to a documentation proposal.

Maintainers review changes before merging. Contributors can propose and discuss; that does not grant direct write access to the repository or access to private CoIS systems.

## Status means something specific

| Label | Meaning |
| --- | --- |
| `status: proposed` | An idea or report submitted for consideration. |
| `status: reviewing` | Maintainers are evaluating the scope, tradeoffs or evidence. |
| `status: accepted` | The direction is accepted; delivery and timing remain uncommitted. |
| `status: implemented` | A specific implementation is linked; verification may still be pending. |
| `status: verified` | A named check, result and limits are linked. This is not universal assurance. |
| `status: deferred` | Work is paused or outside current capacity; the reason should be recorded. |
| `status: declined` | Maintainers chose not to pursue it; the reasoning should remain findable. |

Maintainers should replace the previous status label when changing state, keep useful corrections beside the original proposal, and distinguish partial results from completed work. Topic labels such as `area: privacy` describe subject matter, not approval.

## Credit and decisions

Preserve the original contributor's name or chosen public handle and links when building on an idea. Describe collaborators' actual roles. AI-assisted submissions are welcome; the submitting person is responsible for checking what is published and making the evidence understandable.

When a decision changes, add a dated explanation instead of rewriting the record as though the earlier decision never happened. A compact decision note can include the problem, alternatives, accepted direction, remaining uncertainty, contributor credit and the next step.

Be kind, be specific and challenge ideas without attacking people. See [community guidelines](CODE_OF_CONDUCT.md).
